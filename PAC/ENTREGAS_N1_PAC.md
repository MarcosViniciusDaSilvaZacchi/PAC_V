## 📌 Entrega 2: Iniciação e Definição do Problema (Visão e Requisitos)

> **Objetivo:** Transformar o problema identificado em uma proposta estruturada de Aplicação Web, definindo a visão e elicitando os requisitos com o parceiro.

### 2.1 Documento de Visão
- [x] **Introdução:** Apresentação do Projeto Imigrante Cidadão (Católica SC), diagnóstico da descentralização via WhatsApp e proposta do Portal Imigrante Cidadão como solução web centralizadora.
- [x] **Justificativa:** A descentralização dificulta o acompanhamento das 120h de curso, perde histórico e não atende quem está aprendendo português. A plataforma web resolve isso concentrando materiais, turmas e comunicação.
- [x] **Relevância Social:** Atendimento a ~40 imigrantes/ano (Venezuela, Haiti, Paquistão etc.) em vulnerabilidade e imigração forçada, promovendo inclusão social, acesso à educação, mercado de trabalho e alcance da cartilha informativa.
- [x] **Objetivo Geral:** Desenvolver uma plataforma web responsiva que centralize a distribuição de materiais didáticos, o gerenciamento de turmas e a comunicação entre alunos, professores e administradores do Projeto Imigrante Cidadão.
- [x] **Objetivos Específicos (até 3 etapas a serem percorridas):**
  - [x] 1. Disponibilizar um ambiente único de acesso a materiais didáticos em PDF, organizados por disciplina, substituindo a distribuição via WhatsApp.
  - [x] 2. Estruturar o gerenciamento de turmas e usuários por meio de perfis de acesso distintos (administrador, professor e aluno).
  - [x] 3. Disponibilizar digitalmente a cartilha informativa do projeto, tornando-a acessível a qualquer momento pelos alunos.
- [x] **Identificação de Stakeholders:** Coordenação do projeto (Profa. Glaci Gurgacz), professores/voluntários, alunos imigrantes, equipe de desenvolvimento (Yan e Marcos) e Centro Universitário Católica de SC.
- [x] **Escopo da Proposta:**
  - [x] *In-scope:* Aplicação web responsiva; 3 perfis (Admin, Professor, Aluno); cadastro de professores, disciplinas, materiais didáticos e alunos; visualização digital da cartilha informativa.
  - [x] *Out-of-scope:* App mobile nativo, gamificação, integração com meios de pagamento e arrecadação de doações.

### 2.2 Elicitação de Requisitos
- [x] **Necessidades Identificadas junto ao Parceiro:** Centralização de PDFs em ambiente único; organização das 120h de curso e históricos; interface simples adaptada a não-nativos em português; autonomia para professores; cartilha digital.
- [x] **Requisitos Funcionais (RF):**
  - [x] RF01: O sistema deve permitir que o administrador cadastre professores na plataforma.
  - [x] RF02: O sistema deve permitir que o professor cadastre disciplinas vinculadas às turmas do projeto.
  - [x] RF03: O sistema deve permitir que o professor insira materiais didáticos em formato PDF em uma disciplina.
  - [x] RF04: O sistema deve permitir que o professor edite ou substitua materiais didáticos já inseridos.
  - [x] RF05: O sistema deve permitir que o professor cadastre os alunos matriculados em cada disciplina.
  - [x] RF06: O sistema deve permitir que o aluno visualize os materiais didáticos disponibilizados nas disciplinas em que está matriculado.
  - [x] RF07: O sistema deve disponibilizar a cartilha informativa do projeto em formato digital para consulta dos alunos.
  - [x] RF08: O sistema deve restringir as ações de cadastro e edição de conteúdo apenas aos perfis de administrador e professor.
  - [x] RF09: O sistema deve permitir autenticação (login) individual para os perfis de administrador, professor e aluno.
- [x] **Requisitos Não Funcionais (RNF):**
  - [x] RNF01: Responsividade (desktop e mobile).
  - [x] RNF02: Acesso direto via navegador sem necessidade de instalação.
  - [x] RNF03: Interface simples e intuitiva adequada a usuários com pouca fluência em português.
  - [x] RNF04: Segurança e privacidade de dados em conformidade com a LGPD.
  - [x] RNF05: Compatibilidade com principais navegadores (Chrome, Firefox, Edge, Safari).
  - [x] RNF06: Desempenho adequado mesmo em conexões de internet limitadas.

### 3.2 Arquitetura de Software e Infraestrutura
- [x] **Modelo C4 — Nível 1 (Diagrama de Contexto):** Mapeamento dos 3 atores (Admin, Professor e Aluno Imigrante), da fronteira da aplicação web e do serviço externo de Object Storage.
- [x] **Modelo C4 — Nível 2 (Diagrama de Contêiner):** Detalhamento dos contêineres: SPA Front-end (Vue 3), API RESTful Back-end (Node.js/Express), Banco Relacional (PostgreSQL) e Object Storage (S3 API).

- [x] **Planejamento de Infraestrutura & DevOps:**

  - Back-end em PaaS gerenciada (Render ou Railway).
  - Banco de Dados gerenciado PostgreSQL com rotina de backups.
  - Armazenamento de arquivos em Object Storage compatível com S3 (Cloudflare R2 / AWS S3 / Supabase).
  - CI/CD automatizado via GitHub Actions com testes e deploy contínuo da branch `main`.
- [x] **Stack Tecnológica Definida:**
  - Front-end: Vue.js 3, Tailwind CSS, Pinia, Vue Router, Axios.
  - Back-end: Node.js, Express, Sequelize, JWT, Bcrypt, Multer.
  - Banco de Dados: PostgreSQL.
  - Infraestrutura & DevOps: GitHub, GitHub Actions, Vercel/Netlify, Render/Railway, S3-Compatible Storage.

### 3.3 Modelagem de Dados
- [x] **Modelo DER (Diagrama Entidade-Relacionamento):** Modelagem relacional cobrindo `Usuario`, `Disciplina`, `Matricula`, `Material` e `Cartilha`.
- [x] **Entidades Detalhadas:**
  - `Usuario`: `id` (PK), `nome`, `email` (UK), `senha_hash`, `perfil` (`admin`/`professor`/`aluno`), `data_cadastro`.
  - `Disciplina`: `id` (PK), `nome`, `descricao`, `professor_id` (FK), `criado_em`.
  - `Matricula`: `id` (PK), `aluno_id` (FK), `disciplina_id` (FK), `data_matricula` (N:N entre Aluno e Disciplina).
  - `Material`: `id` (PK), `titulo`, `arquivo_pdf`, `disciplina_id` (FK), `data_upload`, `atualizado_em`.
  - `Cartilha`: `id` (PK), `titulo`, `arquivo_pdf`, `versao`, `data_publicacao` (recurso global institucional).
- [x] **Relacionamentos e Regras de Integridade:** Professor 1:N Disciplinas; Disciplina 1:N Materiais; Aluno N:N Disciplinas (via Matrícula); integridade referencial com `CASCADE`/`RESTRICT` e unicidade de credenciais.
